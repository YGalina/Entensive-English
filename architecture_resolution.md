# ARCHITECTURE RESOLUTION

Дата: 2026-07-15 · Architecture Decision Board — финальное разрешение
Входы: `integrated_learning_blueprint.md` · `learning_experience/` · `adr/ADR-001…020` · `adr/INDEPENDENT_REVIEW_CODEX.md`

**Статус документа: авторитетный имплементационный гейт.**
- **Production** — можно реализовывать.
- **Pilot** — реализуется только внутри валидационного среза, требует подтверждения данными.
- **Shadow Mode** — считается и логируется, **никогда не гейтит обучение**.
- **Research** — экспериментально, вне продукта.
- **Deferred** — намеренно отложено.

Общий вердикт по ревью Codex: **из 20 заключений принято 18, частично отклонено 2** (ADR-005 — в одной детали, ADR-002 — в одной детали). Все шесть сквозных противоречий Codex признаны валидными и разрешены (§ Сквозные). Ничего нового не спроектировано — только разрешение существующего.

## Разрешение по каждому ADR

### ADR-001 · Реестр компетенций → **Production** (модифицирован)
**Codex: принято.** Три исправления входят в решение: (1) один `tier` заменяется тремя независимыми полями — `ontologyStatus` (active/deprecated/merged), `measurementMethod` (direct/inferred/none), `reportingLevel` (shown/aggregated/internal); (2) реестр — **версионируемая таблица** со стабильными UUID, без жёстких enum в бизнес-логике, с поддержкой split/merge/deprecate и маппингом версий (сквозное №6); (3) состав компетенций утверждает Learning Architect, инженер владеет только схемой.
**Почему Production:** это инфраструктура идентификаторов — без неё не пишется ни одна таблица; версионирование снимает риск «цементирования онтологии». 27 записей входят как **v1 содержимого**, а не как вечная истина.

### ADR-002 · Формализм графа → **Production** (формализм); разметка конкретных рёбер → **Pilot**
**Codex: принято частично.** Принято: двух типов рёбер мало — вводятся `hard-prerequisite` / `soft-prerequisite` / `reinforcement` / `co-development` (evidence-dependency живёт в модели оценивания, не в учебном графе); конкретные рёбра (включая D1→D3) не утверждаются без SLA-ревью; ссылка ADR-007→ADR-009 исправлена. **Отклонено с обоснованием:** утверждение, что типизация зависит от ADR-009, — обратное вернее: формализм нужен до движка и независим от него.
**Почему так:** формализм — дешёвое структурное решение (Production); присвоение типа каждому ребру — содержательное SLA-решение (Pilot: ревью специалистом до использования в гейтинге; до тех пор рёбра работают только в рекомендациях).

### ADR-003 · Гейты → **Shadow Mode**
**Codex: принято полностью.** Недостающая альтернатива Codex — «экспертные пороги в shadow mode» — становится решением: предварительные пороги **вычисляются и логируются с первого дня, предсказывают следующий шаг, но не блокируют обучение**. Сверка прогнозов порогов с фактическими исходами — источник калибровки. Состояние `insufficient evidence` — Production (поле модели данных).
**Почему Shadow:** численные пороги — главное «нельзя фиксировать до исследования»; включённые ошибочные гейты вреднее их отсутствия.

### ADR-004 · Аудитория → **Production** (модифицирован) · подпись Галины
**Codex: принято.** «S2-only» отменяется как скрытый ярлык (сквозное №1). Аудитория определяется **измеряемым входным профилем**: (1) достаточное рецептивное понимание материала среза; (2) декларативное знание целевой конструкции присутствует; (3) наблюдаемый дефицит продуктивного извлечения; (4) способность выполнить минимальную устную задачу с опорами; (5) конкретная коммуникативная цель. Онбординг-диагностика проверяет эти пять признаков, а не «уровень».
**Почему Production:** это исполнимое определение для онбординга; ярлык S2 остаётся внутренним шортхендом документации, не критерием.

### ADR-005 · MVP-подграф → **Pilot** (модифицирован)
**Codex: принято частично.** Принято главное: горизонтальный набор дорожек заменяется **вертикальным коммуникативным срезом** — одна законченная речевая задача со всеми минимальными пререквизитами; A3+B1/B2+одна зона C2 — несущие треки среза, слух и произнесение входят как **среда задачи** (вход/выход), не как трекаемые claims. **Отклонено с обоснованием:** упрёк «ежемесячное расширение — календарное без основания» неточен — ADR-005-C уже задавал расширение по критерию (работающие гейты предыдущей дорожки), не по календарю; формулировка сохраняется с заменой «ежемесячно» на «по критерию».
**Почему Pilot:** состав среза — это и есть предмет валидации; фиксировать его как Production до данных нельзя.

### ADR-006 · Живая практика → **Production** (вариант B) · пары и BYO → **Research** · подпись Галины
**Codex: принято.** Для MVP — **B**: живая практика вне core, обещание сужено (ADR-019). Ступенчатая модель C — не принимается, пока не определён и не валидирован confidence-гейт (риск «вечного удержания тревожных снаружи» признан). Недостающая альтернатива **BYO-практика** (свой собеседник, ограниченная доказательность) принимается как research-инструмент вместе с малым пилотом направляемых пар на добровольцах.
**Почему так:** это единственная конфигурация, где продукт не строит marketplace, не считает AI доказательством и не обещает лишнего (сквозное №4).

### ADR-007 · AI: тренировка vs доказательство → **Production** (уточнён)
**Codex: принято (approved с уточнением).** Уточнение входит: требование `partner=human` действует **на F1–F3** (interactional competence), а не глобально; реальная самостоятельная миссия (заказала, спросила, выкрутилась) даёт transfer-evidence для неинтеракционных компетенций без человека-партнёра в записи.

### ADR-008 · Оценивание → **Production** (вариант C) · рубрики → **Research**
**Codex: принято.** MVP не выдаёт proficiency-claims (C). Вариант B пере-определён по ревью: разводятся **model validation** (валидна ли AI-предразметка вообще), **QC-sampling** (контроль качества потока) и **подтверждение конкретного claim ученика** (только человеко-оценённое) — смешение снято. Принята недостающая альтернатива: **слепая двойная разметка исследовательской подвыборки** (без production-сервиса оценки) — как Research для строительства рубрик и inter-rater базы.

### ADR-009 · Адаптация → **Shadow Mode** (движок) · логирование решений → **Production**
**Codex: принято.** Так как ADR-003 в Shadow, движок правил не может гейтить и сам: в MVP последовательность ведёт **кураторская последовательность среза** (принятая недостающая альтернатива «Wizard-of-Oz»: эксперт/куратор задаёт порядок, система логирует, что порекомендовал бы движок). Дополнения Codex входят в спецификацию shadow-движка: minimum dose, cooldown, защита от ежедневного переключения bottleneck, exploration-доля, и **проспективный baseline** (равномерная ротация) в дизайне сравнения — не только офлайн-взгляд назад.

### ADR-010 · Контракт микроцикла → **Production** (модифицирован)
**Codex: принято.** Два изъятия: (1) «receptive-only при наличии сил флагается» — удалено: система не делает выводов о состоянии человека; receptive-only сессия просто легальна и логируется как тип; (2) «N production-циклов как условие валидной недели» — понижено до **рекомендательной недельной нормы** (Shadow: считается, показывается мягко, не гейтит). Остаётся Production: типы сессий; правило, что **введение новой единицы включает produce-попытку в той же сессии** — как свойство контента (см. ADR-011), не как мандат ученику.

### ADR-011 · «T2 в тот же день» → **Production** (как контент-правило) · тайминг-эффект → **Research**
**Codex: принято.** «Produce-дебют ≤48ч» изымается как скрытое жёсткое правило — остаётся исследовательским диапазоном. Production-часть переформулирована так, чтобы не порождать мандата: **каждый вводимый юнит поставляется с produce-задачей в той же сессии** (свойство дизайна контента — исполнимо и проверяемо на 100%); выполняет её ученик сегодня или позже — не гейтится. Естественное сравнение day-0/day-1–2 признано конфаундированным (мотивация, режим) — понижено до Research с осторожной интерпретацией.

### ADR-012 · Тайминг спирали → **Deferred**
**Codex: блок принят.** Evidence-гейтинг темпа неисполним без валидного T4-измерителя (ADR-003 — Shadow, ADR-018 — Research). До их созревания: производственный темп = **кураторская последовательность с календарными дефолтами без claims о прохождении T4**; would-be-гейты считаются в Shadow (данные для будущей калибровки). Разморозка ADR-012 — только после валидации протокола ADR-018 и калибровки порогов ADR-003.

### ADR-013 · Аффективная нагрузка → **Production** (вариант B) · целевая политика → **Research** · подпись Галины
**Codex: принято.** MVP — **без ставок** (B); выход всегда валиден. Все требования ревью входят в research-мандат целевой политики: отдельный safety-review; «N выходов → ступень вниз» заменяется на **нейтральное предложение ступени ниже по выбору ученика** (отказ — не диагностический сигнал и не триггер автоматики); consent withdrawal; data minimization; запрет психологической интерпретации поведения; **три раздельные оси нагрузки** — time pressure / social exposure / evaluative pressure — вместо одной шкалы. Текст политики — авторство Галины.

### ADR-014 · Mastery-контракты → **Production** (концепт, модифицирован) · определения → **Pilot**
**Codex: принято.** Жёсткая привязка «kind → ровно один trajectoryType» смягчена: mastery-контракт назначается **оцениваемому конструкту (evidence target)**; kind объекта даёт дефолтный контракт, составная задача может нести несколько конструктов с разными контрактами. Инвариант «задержка + новый контекст обязательны всем» смягчён для прагматики (социальная уместность требует ещё и вариации собеседника/статуса — фиксируется в контракте типа IV на SLA-ревью). Контракты как поле модели — Production; их содержимое — Pilot (SLA-ревью).

### ADR-015 · Контракт учебного объекта → **Production** (модифицирован)
**Codex: принято полностью.** Схема исправлена: (1) `exposureLog` — **не поле состояния, а отдельный append-only event stream** (EncounterEvent уже есть в learning_data_model_v2 — использовать его); (2) `holdoutFlag` — не свойство объекта, а **отношение learner × object × experiment**; (3) добавляются `contentVersionId` и `sourceLicense`; (4) события экспозиции различают `intentional` (система показала) и `uncontrolled` (жизнь/импорт). Остаётся высшим инженерным приоритетом: append-only encounter/evidence-лог обязателен с первого пилота.

### ADR-016 · Transfer-holdout → **Pilot** (модифицирован таксономией переноса)
**Codex: принято полностью — это сильнейшее возражение ревью.** Концептуальная ошибка признана: полностью необученный item без pretest измеряет prior knowledge + генерализацию, а не перенос освоенного. Принимается **таксономия переноса** (сквозное №5): (a) **item retention** — обученная единица позже; (b) **context transfer** — обученная единица в новой теме/задаче; (c) **structural generalization** — новая единица знакомой конструкции; (d) **real-world transfer** — вне продукта. Валидационный срез обязан иметь **pretest** и matched item sets; каждая метрика помечается своим классом таксономии. 10–15% — не норма, а параметр эксперимента.
**Почему Pilot:** осмыслен только внутри управляемого среза; масштабирование — после данных о contamination.

### ADR-017 · Граница AI → **Production** (вариант B: курируемый банк) · runtime-генерация → **Deferred**
**Codex: принято (approved).** MVP: только заранее собранный и человеко-проверенный банк задач. Runtime-генерация с валидатором — **отдельный будущий ADR** (признано: валидатор формы не гарантирует task-essentiality, отсутствие circumlocution и прагматику — присутствие леммы в задании ≠ обязательность её употребления учеником).

### ADR-018 · Латентность → **Shadow Mode** (сбор) · валидность → **Research**
**Codex: принято.** Рекомендация ADR пересмотрена на C-по-Codex: **никакая латентность не гейтит продукт** — ни текстовая (чтение+орфография+моторика печати ≠ устный доступ), ни голосовая (не валидирована в поле). Обе собираются как research-инструментарий, отделённый от пользовательских гейтов (принята недостающая альтернатива №7). `n≥5` и правило 3σ признаны статистически недостаточными — протокол определит research-пилот repeatability/predictive validity.

### ADR-019 · Результат MVP → **Deferred** (outcome-claim) · mechanism-claim → **Production** · подпись Галины
**Codex: блок принят.** «Начнут выходить сами» семантически = автоматизм (T5) — MVP его не измеряет (сквозное №3); «останутся через недели» — retention, не подтверждённый до среза; B опирается на пере-определяемый transfer (ADR-016). До данных пилота продаётся **опыт и механизм, не эффект**: «тренируешь именно извлечение-в-речь — направление, которого нет у карточек; каждая сессия заканчивается тем, что ты говоришь своё». Outcome-claim формулируется **после** пилота из фактически измеренного (классы и таксономия переноса — по ADR-016). Таблица claim→метрика остаётся артефактом любого релиза.

### ADR-020 · Контент-фильтры → **Pilot** (модифицирован)
**Codex: принято.** Исправления входят: dispersion — не жёсткий гейт для доменной лексики (доменность — легитимная цель); CEFR/регистр-гейты параметризуются задачей; coverage применяется как **рецептивное** требование к материалу; строятся **три отдельных пайплайна**: source material (вход) / target units (учебные единицы) / assessment items (включая holdout). Прогон на 100 кандидатах со SLA-специалистом — условие перевода в Production.

## Сквозные противоречия Codex — разрешение

1. **«S2 — скрытый ярлык».** Принято: вход по пяти профильным признакам (ADR-004). S2 — внутренний шортхенд документации.
2. **«Evidence-гейтинг стоит на отсутствующем измерителе».** Принято: цепочка 003→012→018 разомкнута — 003 Shadow, 018 Research, 012 Deferred; продукт живёт на кураторской последовательности без T4-claims.
3. **«Обещание говорит "само", MVP кончается на T4».** Принято: outcome-claims Deferred; Production-обещание — механизм, не эффект (ADR-019).
4. **«Нет источника human evidence».** Принято: MVP-claim без human transfer + малый research-пилот пар + BYO с ограниченной доказательностью (ADR-006/007).
5. **«Holdout смешивает три конструкта».** Принято: таксономия переноса + pretest + matched sets (ADR-016).
6. **«Полный реестр цементирует онтологию».** Принято: версионируемый реестр, UUID, без enum, split/merge/deprecate (ADR-001/015).

Недостающие альтернативы Codex №1–9: все девять инкорпорированы в решения выше (shadow-режим → 003/009/018; Wizard-of-Oz → 009; BYO → 006; профильный вход → 004; вертикальный срез → 005; без outcome-claim → 019; отдельный research-инструментарий → 018; версионируемая онтология → 001; таксономия переноса → 016).

## ИМПЛЕМЕНТАЦИОННЫЙ ГЕЙТ

### PRODUCTION — можно реализовывать
1. Версионируемый реестр компетенций: UUID, ontologyStatus/measurementMethod/reportingLevel, маппинг версий (001).
2. Типизированный граф (4 типа рёбер) как структура данных; рёбра — только в рекомендациях до SLA-ревью (002).
3. Состояние `insufficient evidence` в модели оценивания (003-часть).
4. Онбординг-диагностика по пяти профильным признакам входа (004).
5. Разделение AI-тренировки и доказательства: `partner`-поле; human-требование на F1–F3; solo-миссии как evidence неинтеракционных компетенций (007).
6. MVP без proficiency-claims (008-C).
7. Логирование каждого решения секвенирования с версией правил (009-часть).
